# IR-01 и IR-02: промежуточная модель Смуты и проверка допуска

Реализовано 16 октября 2026 года: `tools/smuta_build/ir.py`, JSON-формат
`format: smuta-ir`, `schema_version: 1`. Это исследовательская модель в исходных
единицах. Генерации UZDoom и исполнения игровой логики на этом этапе нет.

## Команды и границы этапа

```powershell
.\tools\Build.ps1 -Task IR
# Новый или пустой каталог внутри build/ либо dist/:
.\tools\Build.ps1 -Task IR -Output .\build\ir\smuta-review
.\tools\Build.ps1 -Task Test
.\build\tools-venv\Scripts\python.exe -B .\tests\verify_ir.py
```

Результат — `build/ir/smuta/ir.json`. CLI:
`python -B -m smuta_build ir --source DAT --output DIRECTORY` с `PYTHONPATH=tools`.
Источник по умолчанию тот же, что у TXT-01. Команда `Build` по-прежнему выполняет
извлечение и проверку DAT; IR запускается отдельно. Существующий результат
не перезаписывается. JSON записывается в ASCII-представлении, компактно,
с завершающим LF; байт 98 остаётся обратимым `\udc98`.

`parse_level` отвечает за синтаксис, `lower_document` принимает его результат
и каталог DAT-02, `build_model` связывает этапы, `write_model` сохраняет модель.
Декодированный документ не изменяется. Модель не зависит от ZScript, UDMF
или запуска игры. `read_model` отклоняет другой формат/версию; это проверка
версии; проверка IR-02 выполняется отдельно с исходным DAT. Будущие несовместимые изменения
требуют новой версии и явной миграции, а не угадывания отсутствующих полей.

## Структура v1

| Поле | Содержание и смысл |
| --- | --- |
| `catalog` | Все записи DAT, включая дубликаты. Для каждой: игра, хеш контейнера, индекс, имя и его байты, диапазон и хеш данных. |
| `resources` | Все 42 текстовых ресурса в порядке каталога, без автоматического назначения кампании. |
| `resources[].decoded` | Полный результат TXT-01: строки с точными байтами, события, сетки, контексты, диагностика. Это сохраняет также неинтерпретированные поля, комментарии и исходное форматирование. |
| `definitions` | Упорядоченные шаблоны с общими полями, классом, параметрами, контекстными ресурсами и исходным хвостом. Повторы не объединяются. |
| `settings` | Последовательность присваиваний Game Ini; порядок и повторы сохранены. |
| `source_units` | Исходные Cell Side/Cell Height; коэффициенты переноса, мировые оси, начало координат и единица времени — `null` до исследования. |
| `grids` | Обе сетки с исходными байтами строк и таблицей всех определений-кандидатов для каждого ключа. Роль FCMap пока не объявлена доказанной. |
| `instances` | Одна запись-кандидат на каждую ячейку TMap, включая пробелы и ячейки без определения. Это не команда создать актор UZDoom. |
| `materials` | Привязки исходных хвостов поверхностей типов 0/12/13 к определениям; статус `opaque`. |
| `resource_references` | Байтовое имя, роль, исходная позиция, ID выбранного ресурса либо `null`, статус разрешения в каталоге. |
| `definition_links` | Символьные ссылки снаряда/выпадения врага со всеми определениями-кандидатами; непрозрачные сенсорные связи сохраняются с исходным хвостом. |
| `animations` | Ссылки Flic и анимационных полей; направления, кадры и единицы задержек — `null`, статус `not-decoded` до GFX-02. |

Идентичность ресурса: `smuta:<sha256 контейнера>:<индекс>`.
Определения добавляют `/definition/<порядковый номер>`, сетки — `/grid/<имя>`,
экземпляры — `/grid/TMap/<столбец>/<строка>`. Область стабильности — тот же
контейнер и версия схемы; имя DAT не является идентификатором или путём.
Ссылки ресурсов получают отдельные ID событий, даже при одинаковом имени.

`origin.offset/end` — байтовый диапазон от начала текстового ресурса,
`origin.line` — строка с 1; абсолютное смещение равно `source.offset + offset`.
У параметров сохраняется полный токен TXT-01 с диапазоном и байтами.
Позиция экземпляра — столбец/строка с 0 в исходном порядке. `source_offset`
указывает непосредственно на байт ячейки. Мировые координаты, высота, направление
осей и угол разворота карты не выводятся из этих индексов. FCMap сохраняется
целиком и не превращается во второй набор акторов.

## Семантика и неизвестные

Основание имён полей и классов — [статическое исследование EXE](SMUTA_EXE_LOGIC.md):
фабрика `0041DDC0`, общие поля `0041E2C4–0041E324`, загрузчики классов
из таблицы исследования. Правило ссылок — DAT-02, точные байты CP1251,
первое совпадение; его EXE-хеш и VA записаны в `resolution_policy`.
Эти сведения описывают применённые правила, а не доказывают происхождение
произвольного входного DAT от этого EXE.

Пять общих полей названы `type/flags/scale/vertical/mapColor`.
Отсутствующее поле **не добавляется**: восемь строк SM-U21 остаются с четырьмя
полями. Тип 11 и неизвестный тип получают `class: null`; не создаётся класс
по умолчанию. Числа хранятся до машинного приведения к int16/byte, без обрезания.

Разобраны подтверждённые префиксы хвостов игрока, предмета, базового актора,
двери, снаряда, врага и оружия (типы 1/3/5/7/8/9/10). Порядок и неизвестные
параметры игрока обозначены индексами `player00…player10`; это не новый словарь
ТТХ. Знаки здоровья, скорости и урона не меняются. `tail_raw` всегда хранит
весь хвост, `remainder_raw` — точный остаток после разобранного префикса,
включая пробелы перед сообщением. При неполном/нечисловом префиксе ставится
`incomplete-prefix`; подстановки нет. Числа не объявлены миллисекундами,
координатами Doom или итоговым уроном.

Наследуемые хвосты поверхностей и сенсоров пока непрозрачны. Их реальные байты
и позиции сохранены; модель не угадывает цель сенсора по последнему токену.
У каждого определения отдельно сохранены все три контекста Sprite/Flic/Sound,
включая исходную строку Sprite с необязательным числом. Ресурсная ссылка
означает только наличие имени в каталоге, не подтверждение формата, назначения
кадра, прозрачности или использования контекста конкретным классом.

`definition_ids` у экземпляра и `target_definition_ids` у связи — список всех
кандидатов: пустой список сохраняет отсутствие определения, несколько ID —
неоднозначность. Выбора «последний победил» нет. `_` преобразуется только
в определениях TXT-01, но не в ячейках и не в символьных ссылках хвоста.
Связи по символам не разрешаются автоматически в конкретный экземпляр.

`new_instance_state(instance)` создаёт независимые позицию и `runtime`,
со статусом `not-initialized`. Изменение такого состояния не затрагивает
шаблон, другой экземпляр или исходную модель. Пустой `runtime` означает, что
конструктор/сброс оригинала ещё не исполнен; это не нулевое игровое состояние.
Назначение вариантов сложности и маршрута остаётся `campaign_assignment: null`.

Все документы и корень имеют `release_ready: false`. Здесь нет заглушек
игровой логики. IR-02 добавляет отдельную проверку допуска и запрет релизной
упаковки, описанные ниже. Схема IR v1 не меняется.

## IR-02: отчёт покрытия и режимы упаковки

Реализовано 16 октября 2026 года в `tools/smuta_build/validation.py`.
Проверка повторно строит модель из DAT и сравнивает весь JSON с проверяемым IR,
включая каталог, декодированные строки, сетки, экземпляры, параметры, контексты,
происхождение, ссылки и правило первого совпадения DAT-02. Пропуск документа,
ячейки любой сетки или экземпляра, подмена ссылки либо `release_ready` дают
`source-model-mismatch`. Поля готовности и статусы из входного JSON не служат
доказательством. Текущая версия требует точного результата IR-01; расширение
модели доказательствами реализации потребует явного развития схемы и валидатора.

```powershell
.\tools\Build.ps1 -Task Validate -IR .\build\ir\smuta\ir.json -Output .\build\ir\coverage.json
# Сохраняет отчёт, затем завершается ненулевым кодом при блокировках:
.\tools\Build.ps1 -Task Validate -IR .\build\ir\smuta\ir.json -Output .\build\ir\release-check.json -Mode release
# Stage — явно подготовленный каталог; результат маркирован как исследовательский:
.\tools\Build.ps1 -Task Pack -Stage .\build\stage -Archive .\build\research.pk3 -IR .\build\ir\smuta\ir.json -Mode research
# Тот же вход блокируется до создания архива:
.\tools\Build.ps1 -Task Pack -Stage .\build\stage -Archive .\dist\smuta.ipk3 -IR .\build\ir\smuta\ir.json -Mode release
.\build\tools-venv\Scripts\python.exe -B .\tests\verify_validation.py
```

CLI: `validate --source DAT --ir IR_JSON --output REPORT_JSON --mode research|release`;
`pack --source STAGE --output ARCHIVE --mode research|release --ir IR_JSON --dat-source DAT`.
Отчёт `smuta-ir-validation`, версия 1, сохраняется без перезаписи в `build/`
или `dist/`. Порядок стабилен, даты и абсолютные пути не записываются.
Проверка исследовательского режима допускает неизвестную семантику, но требует
целостности IR; релизный режим требует также отсутствия всех блокировок.

`coverage` считает все документы и записи каталога, определения, обе сетки,
ячейки с единственным/отсутствующим/неоднозначным определением, экземпляры,
ссылки по статусам, типы используемых определений, анимации и диагностику текста.
База покрытия — повторно построенный источник (`coverage_basis`), а не
потенциально испорченный входной IR; применимость к нему задаёт `integrity_ok`.
Тексты с `[Game Ini]` вне распознаваемых имён дополнительно блокируют релиз.

Использование определения консервативно считается по **обеим** сеткам и
транзитивным ссылкам снаряда/выпадения. Неизвестная роль сетки не позволяет
исключать её содержимое. Связи с несколькими кандидатами, отсутствующие цели,
непрозрачный sensor-tail, неполные общие поля (SM-U21), неизвестный класс,
непроверенные хвосты и механики используемых определений блокируют релиз.
Ресурсные директивы проверяются все, даже если использование контекста ещё
не доказано. Дубликат DAT сам по себе не является неоднозначностью: доказанное
первое точное совпадение разрешает его; все записи остаются в каталоге.

Дополнительные блокировки: недекодированные анимации/материалы, непроверенные
пространственные и временные единицы, неназначенная кампания, отсутствие
генерации и игровой сверки. Разобранный префикс не снимает блокировку механики.
Валидатор не читает Markdown-таблицу реестра как машинную политику и не считает
закрытие строки в ней доказательством готовности IR. SM-U10, например, остаётся
под блокировкой используемого предмета, без исполнения неизвестного Apply.

Каждая проблема содержит код, владельца, исходную позицию там, где она есть,
и `blocks_release`. Для ячеек проблемы агрегированы по сетке и байту ключа
с числом затронутых ячеек. `research_placeholders` явно перечисляет пропуски
реализации со статусом `unimplemented-no-runtime-substitution`: это список
нереализованных частей, а не созданные игровые заменители. Никакая игровая
логика или значение по умолчанию здесь не подставляется.

Упаковщик повторяет проверку непосредственно перед записью: сохранённый отчёт
не является пропуском. В research/release резервируется имя
`smuta-build-report.json`; оно добавляется в архив с режимом, отчётом и
`playable_game_verified: false`. Коллизия имени, в том числе по регистру,
отклоняется. Исследовательский пакет может быть техническим макетом и не
обязан запускаться. Текущий IR v1 **всегда блокирует релиз**: доказательства
реализации и сравнения ещё отсутствуют. Разрешающего переключателя нет.
Сырая упаковка (`raw`, по умолчанию) разрешена только в `.zip` и ничего не
утверждает о готовности игры; `.pk3`/`.ipk3` требуют явного режима и DAT/IR.

### Приёмка IR-02

CPython 3.14.6, Windows PowerShell 5.1, UZDoom PE 5.0.3; хеши DAT, EXE
и движка совпадают с приведёнными в приёмке IR-01 ниже. Эталон — Smutabor
Patch. Прошли 46 автономных тестов, включая 9 новых тестов IR-02: порча
IR/копии decoded, потеря ячейки/каталога/документа, подмена ссылки и готовности,
пропавшие ресурсы, дубликаты DAT, неоднозначные определения/связи, транзитивное
использование неизвестного класса, неполные поля, отказ релиза, сохранение
отчёта и ненулевой CLI-код, маркировка и воспроизводимость пакета.

Локальная интеграционная приёмка подтвердила 460 записей каталога, 42 текста,
6127 определений, 84 сетки, 344064 ячейки и 172032 экземпляра-кандидата.
Все 18212 ресурсных ссылок разрешены; это не означает разбор ссылок внутри
непрозрачных хвостов. 261766 ячеек имеют единственное определение-кандидат,
82298 — не имеют определения в текущей модели. Последнее не объявлено ошибкой
оригинала: трактовка пустых/особых ячеек ещё требует исследования; релиз
консервативно блокируется. Неоднозначных определений ячеек на этом DAT нет.
Используются 4390 определений с учётом обеих сеток и замыкания ссылок;
для четырёх из них обнаружены неполные общие поля. Сохранены все восемь
исходных неполных определений, включая невыбранные текущим анализом использования.

Два отчёта и два исследовательских пакета побайтно совпали. SHA-256 отчёта:
`c00f6eb914210d7044d655bb59e7656e59faa1714be7251ea02be0619bb7281b`.
Релизный IPK3 не создан; PowerShell `Validate -Mode release` сохранил отчёт
и вернул ненулевой код. Хеши исходных DAT, EXE и UZDoom до/после совпали.
Журнал: `build/ir-02 verification 5b45c5959635479f95fa1187d6bbd97c/report.json`.
Игры не запускались: проверка статическая, точность поведения, масштабов,
таймингов и прохождения не подтверждена.

## Статическая приёмка

CPython 3.14.6, Windows PowerShell 5.1; локальный UZDoom PE 5.0.3.
Источник — Smutabor Patch, а не неизменённая версия 1997 года:

```text

uzdoom.exe e6df57d1027cee089d33388ab743817a236148992ac3881d9141ea2b547677d9
```

Прошли 37 автономных тестов, включая 7 новых для IR. Интеграционная проверка
нашла 42 текста независимо по содержимому, сверила каталог из 460 записей,
6127 определений, 84 сетки и все 344064 байта ячеек, 172032 экземпляра-кандидата
TMap, контексты и исходные позиции параметров. Все 18212 ресурсных ссылок
модели разрешились в первое точное совпадение DAT. Это не проверка всех ссылок
непрозрачных хвостов. 4727 префиксов разобраны; 1400 хвостов оставлены непрозрачными,
в том числе неполные общие поля. Анимации не декодировались.

Два результата побайтно совпали; SHA-256 `ir.json`:
`ac5e8f1a955f4ef4b9e72f6ad591017de348ceee111afb13ba7a918b4960ef9a`.
Проверены отказ перезаписи, отказ неизвестной версии и независимость состояния.
Хеши DAT, EXE и UZDoom до и после совпали. Журнал:
`build/ir-01 verification 0a93824c16ad425c9e5ca0587ad9561a/report.json`.

Игры не запускались. Геометрия, масштаб, задержки, поведение объектов и
прохождение не проверены; статическая приёмка подтверждает сохранность
и воспроизводимость модели, а не точность игровой реализации.
