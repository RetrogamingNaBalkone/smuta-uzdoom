# GFX-03: шрифты, экраны и освещение Смуты

Статическое исследование и декодеры выполнены 17 октября 2026 года.
Исследован **Smutabor Patch**, а не неизменённая игра 1997 года:

```text
SMUTA.DAT  6e13c4b65e4530291b11e3d4cd6280d874c489837e7e74c5f53b686ca69a74e8
SMUTA.EXE  1b7f8e5d010e225139f3a03f3721aff39d5e0b8c1c4ef42106c14002ea6405bb
```

UZDoom PE **5.0.3** при этой проверке не запускался. Хеш движка и остальных
входов записан в отчёте приёмки. Правила ниже — выводы из DAT и кода EXE;
игровые замеры и проверка переноса освещения в UZDoom ещё не выполнены.

## Шрифты и карта символов

Записи **187 FONT8** (2048 байт) и **188 FONT16** (4096 байт) содержат
256 последовательных глифов шириной 8 и высотой 8/16. Байт задаёт строку,
старший бит — левый пиксель, строки идут сверху вниз.
Загрузчик `004264C0–0042650A` получает высоту делением длины на 256;
рисование `00426592–0042664A`, маски `0043732C–0043733B`:
`80 40 20 10 08 04 02 01`. Глифы и атласы обоих шрифтов просмотрены.
При запуске EXE выбирает именно FONT8 (`00424F1B–00424F25`). Для FONT16
прямого строкового ключа в исследованном EXE не найдено: его использование
остаётся неизвестным; это не доказательство неиспользования.

Текст поступает как байты CP1251. Перед обращением к шрифту EXE вычисляет:

| Байт текста | Индекс глифа |
| --- | --- |
| `00…7F` | байт без изменения |
| `80…EF` | байт − `40h` |
| `F0…FF` | байт − `10h` |

Таким образом, `А…п` (`C0…EF`) рисуются глифами `80…AF`, `р…я`
(`F0…FF`) — глифами `E0…EF`. Для русского алфавита А…я это соответствует
позициям CP866. **Весь шрифт автоматически объявлять CP866 нельзя:**
FONT16 содержит изменённые служебные глифы; область `80…BF` входного текста
тоже преобразуется, а отдельного правила для `Ё/ё` нет.
Байты CP1251 `A8/B8` попадают в глифы `68/78` (`h/x`). Автоматическое
исправление этого поведения в декодер не внесено. Прочие расширенные символы
не получают подтверждённой Unicode-семантики. Неопределённый CP1251 `98`
сохранён в карте как байт с номером глифа и `cp1251: null`.

Строковый потребитель `0042664B–004266A2` завершает вывод по `00` **или `$`**,
игнорирует CR, LF начинает новую строку; шаг X задаётся runtime-полем +24h
(по умолчанию равен высоте после загрузки), шаг Y — высотой +26h.
Это не универсальное правило для сеток уровней: их парсер не меняется.
Режим 1 оставляет фон глифа нетронутым, остальные ветви рисуют цвет фона;
цвета задаются потребителем, не самим FONT.

Экспорт сохраняет все 256 глифов каждого шрифта, исходные байты, бинарные
пиксели в порядке глиф/строка/X и PNG-атлас 16×16 глифов. `characters.json`
содержит карту всех 256 входных байтов, номера глифов, управляющие символы
и признак подтверждённого Unicode. PNG — чёрно-белое превью без назначенной
игровой прозрачности. Для UI-01 потребуется сохранить правила строк и явно
решить поведение Ё/ё, а не заменять весь шрифт системным.

Не назначаем Z0 финальным экраном по одному номеру: функция выбирает текущий

назначенного «экрана победы» из этих файлов не установлено; финальная
последовательность и подтверждения остаются RES-06/UI-01.

Фон справки хранится внутри DAT, внешний HELP.SPR не требуется. Изображение
записи 335 просмотрено: рамка и заголовок «ПОМОЩЬ», без текста управления.
Текст интерфейса задаётся отдельно от фонового SPR.
Рисование фона установлено по коду; обработку ввода и возврат в меню
ещё должна проверить UI-01 в работающем эталоне.

## LIGHT1: три области, а не 352 одинаковые таблицы

Запись **190**, 90 112 байт. Загрузка директивы `[Light] Light = LIGHT1`
в `00427533–004275C5` передаёт указатель в `00410EA8–00410F03`.
Последняя функция копирует три области по 2000h, 4000h и 10000h байт:

| Смещение в ресурсе | Длина | Содержание | Обращение |
| --- | --- | --- | --- |
| `0` | 8192 | 32 ступени × 256 индексов палитры | `data[level*256 + pixel]` |
| `8192` | 16384 | 32 × 256 little-endian RGB555 | `u16(data, 8192 + 2*(level*256 + pixel))` |
| `24576` | 65536 | Таблица смешивания двух индексов | `data[24576 + source*256 + destination]` |

В runtime первая область имеет отдельный выровненный указатель по +4,
вторая начинается по +8, третья — по +A008. Эти адреса **не являются
смещениями в DAT**. В частности, промежуток runtime +4008…+A007 не хранится
как четвёртая область LIGHT1. Генератор дополнительных цветовых таблиц
в `00410810…` также не меняет формат сериализованных 90 112 байт.

Маскированное смешивание `00407082–004070A3` помещает исходный пиксель в AH,
пиксель фона в AL, затем читает таблицу по этому 16-битному индексу.
Исходный ноль пропускается **до** смешивания. Порядок аргументов значим:
64 416 из 65 536 пар отличаются при перестановке. Таблица не заменяется
обычной полупрозрачностью; её байты сохраняются целиком. Формулу генерации
ближайшего цвета и коэффициенты смешивания для воспроизведения угадывать
не требуется: исследованный эталон загружает готовые данные.

Для RGB6-компоненты `c` палитры GAMEP1 на ступени `l = 0…31`:

```text
v = floor(c * (32 - l) / 32)
RGB555 = ((vR >> 1) << 10) | ((vG >> 1) << 5) | (vB >> 1)
RGB565 = ((vR >> 1) << 11) | (vG << 5) | (vB >> 1)
```

**Проверка по данным:** все 8192 RGB555-значения LIGHT1 совпадают с этой
формулой для GAMEP1, старший бит нигде не установлен. GAMEP1 и
`ЗАСТАВКА_ПАЛ` — разные палитры, взаимозаменяемыми они не объявляются.
`00410B64–00410CA8` пересчитывает direct-color-таблицу при смене палитры:
режим 2 использует RGB565, другая ветвь RGB555. `00424E00–00424E1D`
явно выбирает режим 2 и пересчёт. Поэтому сериализованную RGB555 нельзя
безусловно принять за итоговый цвет этой современной сборки.

Выбор таблицы стен в `00402B93–00402C12` вычитает 16-битный `LightEdge`,
обнуляет отрицательный результат, делит на `LightStep` и ограничивает ступень
31. В индексном режиме шаг таблицы 256 байт, в direct-color — 512.
Есть другие пути (например, `00402573–004025AA` сдвигает на 8 вместо деления);
это не доказательство одной универсальной формулы яркости для всех поверхностей.
`LightEdge/LightStep` в `[Game Ini]` и ссылка `Light` в `[Light]` — разные вещи.
Формулы расстояния, все пути полов/потолков и изменение палитры при эффектах
требуют интеграции и сравнения; в декодер не добавлено предположение о Doom light level.

**Решение для переноса:** сохранить исходный индекс пикселя и ступени;
индексную ветвь воспроизводить точным lookup LIGHT1 с последующим GAMEP1,
direct-color — по соответствующей таблице/пересчёту палитры. Смешивание
воспроизводить отдельно с учётом порядка и маски. Не запекать единственное
освещение в исходную текстуру и не назначать стандартный COLORMAP по размеру.
`Light.shade`, `Light.mix`, `direct_colors` реализуют эти операции над данными;
шейдер/генератор и отображение в UZDoom пока не реализованы.

Графические форматы проверены декодерами целиком. Для WAV здесь проверены
сигнатура и внешний диапазон RIFF; разбор чанков и воспроизведение — SND-01.
Неизвестных **форматов** не осталось. Это не означает, что установлены все
**условия использования**: у большинства записей сохранён статус
`consumer-context-required`, у 183 — `shadowed-by-first-match`.
Наличие декодируемого ресурса или отсутствие прямого ключа в EXE не означает
его участия/неучастия в кампании. Неизвестные обязательные потребители
по-прежнему блокируют релиз.

## Воспроизведение и приёмка

```powershell
./tools/Build.ps1 -Task AuxGraphics
./tools/Build.ps1 -Task Test
./build/tools-venv/Scripts/python.exe -B ./tests/verify_auxgraphics.py
```

Выход по умолчанию — `build/decoded/smuta-auxgraphics/`; каталог должен быть
новым/пустым, иначе задайте `-Output`. Модуль `auxgraphics` отделён от SPR/FL
и игрового генератора. Манифест v1 хранит происхождение трёх ресурсов,
происхождение палитры для пересчёта, хеши файлов, карту символов и каталог.
[Профиль](../profiles/smuta/auxgraphics.json) содержит роли экранов и диапазоны
EXE с VA, файловыми смещениями, длинами и SHA-256; приёмка проверяет их
через таблицу секций PE. Профиль привязан к точным хешам DAT/EXE.

Прошёл **71 автономный тест**. Интеграционная приёмка проверила все 460
строк против исходного CSV, обратное упаковывание 512 глифов, PNG-атласы,
8192 RGB555, доказательства EXE, 11 экранов, хеши каждого выхода,
отказ перезаписи и два побайтно одинаковых экспорта. Хеши всех файлов папки
Смуты, `uzdoom.exe` и `uzdoom.pk3` до/после совпали.

Снимок результата: [gfx03-results.json](research/gfx03-results.json).
Полный локальный отчёт указан в нём. Извлечённые изображения и таблицы остаются
в `build/`. Сверка с запущенными играми не проводилась; `release_ready: false`.
GFX-03 выполнена как статический разбор и подготовка данных. Полная приёмка
освещения в сценах, навигации интерфейса и финала остаётся CHECK-02/UI-01/RES-06.
